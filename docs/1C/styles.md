# Стили представления содержимого контейнеров 1С

## Назначение документа

Документ описывает шесть стилей представления содержимого файлов-артефактов 1С (.epf, .erf, .cf, .cfe) на виртуальной панели FAR Manager и при распаковке на диск. Стили определяют, каким образом внутренняя структура CF-контейнера (набор строк `rows_map: HashMap<String, Vec<u8>>`) трансформируется в дерево `VfsEntry`, отображаемое пользователю.

Каждый стиль реализует трейт `PresentationStyle` ([mod.rs](../../src/v8/styles/mod.rs)):

```rust
pub trait PresentationStyle: Send + Sync {
    fn build_vfs(&self, rows_map: &HashMap<String, Vec<u8>>)
        -> Result<Vec<VfsEntry>, BuildVfsError>;
    fn sync_vfs_to_rows(&self, vfs: &[VfsEntry], updates: &mut HashMap<String, Vec<u8>>);
}
```

Стиль выбирается в настройках плагина (`UnpackStyle` в [settings.rs](../../src/far/settings.rs)) и применяется при отображении панели и при распаковке (Shift+F2).

---

## Контекст: физическая структура контейнера

Прежде чем описывать стили, необходимо понимать, что содержит `rows_map` — результат разбора физической структуры CF-контейнера (см. [processing.md](processing.md), раздел 3).

CF-контейнер хранит данные как набор **строк** (rows), каждая из которых имеет:

- **ID** — текстовый идентификатор (UUID, имя типа `root`, `version` и т.д.)
- **Body** — бинарное тело (может быть сжатым DEFLATE)

После чтения контейнера `rows_map` содержит пары `ID → распакованные данные`:

```
rows_map = {
    "root"                                  → метаданные корневого объекта
    "version"                               → версия формата
    "versions"                              → версии вложенных объектов
    "a1b2c3d4-..."                          → заголовок объекта метаданных
    "a1b2c3d4-....0"                        → тело объекта (модуль или вложенный контейнер)
    "e5f6a7b8-..."                          → заголовок формы
    "e5f6a7b8-....0"                        → тело формы (модуль)
    ...
}
```

Тела могут быть:

- **Текстом** (UTF-8 с BOM) — скобочная структура метаданных, код модуля
- **Вложенным контейнером** (начинается с сигнатуры `0x7FFFFFFF`) — содержит собственные строки
- **Бинарными данными** — макеты, картинки

## 1. Raw — бинарные блобы

**Файл реализации:** [raw.rs](../../src/v8/styles/raw.rs)

### Назначение

Отображение содержимого контейнера «как есть», без семантической интерпретации. Каждая строка контейнера показывается как отдельный файл с именем, равным ID строки.

### Целевая аудитория

- Отладка и анализ структуры контейнера
- Исследование неизвестных или повреждённых файлов
- Низкоуровневый доступ к данным

### Алгоритм `build_vfs`

1. Перебрать все записи `rows_map`.
2. Для каждой записи `(id, data)` создать `VfsEntry::File`:
   - `name` = `id` (например, `root`, `a1b2c3d4-e5f6-...`, `a1b2c3d4-e5f6-....0`)
   - `data` = распакованное тело строки (после inflate, если было сжато)
   - `origin_row_id` = `id` (для обратной записи)
3. Отсортировать файлы по имени.

### Пример вывода для .epf

```
root
version
versions
a1b2c3d4-e5f6-7890-abcd-1234567890ab
a1b2c3d4-e5f6-7890-abcd-1234567890ab.0
d5b0e5ed-256d-401c-9c36-f630cafd8a62
d5b0e5ed-256d-401c-9c36-f630cafd8a62.0
```

### Алгоритм `sync_vfs_to_rows`

Прямое отображение: для каждого `VfsEntry::File` с `origin_row_id` обновить `updates[row_id] = data`. Данные записываются без трансформации.

### Особенности

| Свойство | Значение |
|----------|----------|
| Плоская структура | ✅ Да — все файлы на одном уровне |
| Имена файлов | UUID строк контейнера |
| Семантика | Нет — имена не несут смысла |
| Вложенные контейнеры | Не раскрываются — отображаются как бинарный блоб |
| Поддержка R/W | ✅ Полная — прямое отображение |
| Совместимость с другими инструментами | Нет — формат специфичен |

## 2. Full-parse — структурированные файлы

**Файл реализации:** [full_parse.rs](../../src/v8/styles/full_parse.rs)

### Назначение

Полная распаковка контейнера с сохранением внутренней иерархии, включая служебные метаданные. Каждый вложенный контейнер рекурсивно раскрывается в поддиректорию. Текстовые файлы сохраняют оригинальный формат (скобочная структура `{...}`).

### Целевая аудитория

- Глубокий анализ внутренней структуры метаданных
- Отладка парсера и контейнера
- Доступ к служебным полям, скрытым в семантических стилях

### Алгоритм `build_vfs`

1. Перебрать все записи `rows_map`.
2. Для каждой записи `(id, data)`:
   a. Определить тип содержимого:
      - Если `data` начинается с сигнатуры контейнера (`0x7FFFFFFF` или `0x7FFFFFFF7FFFFFFF`):
        → это **вложенный контейнер**. Создать `VfsEntry::Dir` с именем `id`, рекурсивно разобрать вложенный контейнер и добавить его строки как дочерние элементы.
      - Если `data` начинается с UTF-8 BOM (`0xEF 0xBB 0xBF`):
        → это **текстовый файл**. Создать `VfsEntry::File` с расширением, определённым по содержимому:
        - Если содержит `{` на верхнем уровне → `.txt` (скобочная структура)
        - Если содержит ключевые слова BSL (`Процедура`, `Функция`, `Procedure`, `Function`) → `.bsl`
        - Иначе → `.txt`
      - В остальных случаях:
        → **бинарный файл**. Создать `VfsEntry::File` с расширением `.bin`.
   b. Имя файла формируется как `id` + определённое расширение.
3. Отсортировать элементы:
   - Сначала директории (вложенные контейнеры), затем файлы
   - Внутри каждой группы — лексикографически по имени

### Пример вывода для .epf

```
a1b2c3d4-e5f6-7890-abcd-1234567890ab/
│   ├── module.bin
│   └── text.bsl
d5b0e5ed-256d-401c-9c36-f630cafd8a62/
│   ├── form_data.txt
│   └── text.bsl
root.txt
version.txt
versions.txt
```

### Алгоритм `sync_vfs_to_rows`

1. Обратный обход дерева VFS.
2. Для `VfsEntry::File` с `origin_row_id`:
   - Записать `data` в `updates[row_id]`.
3. Для `VfsEntry::Dir` с `origin_row_id`:
   - Собрать дочерние элементы обратно во вложенный контейнер с помощью `ContainerWriter`.
   - Записать результат в `updates[row_id]`.

### Особенности

| Свойство | Значение |
|----------|----------|
| Иерархическая структура | ✅ Да — вложенные контейнеры раскрываются |
| Имена файлов | UUID + расширение по типу содержимого |
| Семантика | Частичная — расширения `.bsl`/`.txt`/`.bin` по эвристике |
| Вложенные контейнеры | ✅ Раскрываются рекурсивно |
| Служебные файлы | ✅ Показываются (root, version, versions) |
| Поддержка R/W | ✅ Полная с обратной сборкой вложенных контейнеров |
| Совместимость | Нет — формат специфичен для far1c |

## 3. V8Unpack — совместимый формат (.header + .data)

**Файл реализации:** [v8unpack.rs](../../src/v8/styles/v8unpack.rs)

### Назначение

Представление содержимого контейнера в формате, совместимом с классическим инструментом [v8unpack](https://github.com/aspect-ru/v8unpack). Каждая строка контейнера раскладывается на два файла: `.header` (заголовок строки: timestamps, атрибуты) и `.data` (тело строки). Вложенные контейнеры рекурсивно распаковываются в поддиректории.

Этот формат является де-факто стандартом для низкоуровневой работы с CF-контейнерами в экосистеме 1С.

### Целевая аудитория

- Пользователи v8unpack, привыкшие к этому формату
- Миграция данных между far1c и v8unpack
- Интеграция с существующими скриптами обработки

### Алгоритм `build_vfs`

1. Перебрать все записи `rows_map`.
2. Для каждой записи `(id, data)`:
   a. Определить, является ли `data` вложенным контейнером (проверка сигнатуры `0x7FFFFFFF`).
   b. Если **вложенный контейнер**:
      - Создать `VfsEntry::Dir` с именем `id`.
      - Рекурсивно разобрать вложенный контейнер.
      - Каждую строку вложенного контейнера представить парой `.header` + `.data`.
   c. Если **конечный payload**:
      - Создать два файла:
        - `VfsEntry::File { name: "{id}.header", data: row_header_bytes }` — бинарный заголовок строки (20 байт: 2×datetime + attributes, см. [processing.md](processing.md), п. 3.1 «RowHeader»).
        - `VfsEntry::File { name: "{id}.data", data: row_body_bytes }` — тело строки.
3. Отсортировать элементы по имени.

### Формат файла `.header`

Бинарный файл, 20 байт:

| Смещение | Размер | Содержание |
|----------|--------|------------|
| 0 | 8 | Время создания (FILETIME, little-endian) |
| 8 | 8 | Время модификации (FILETIME, little-endian) |
| 16 | 4 | Атрибуты (uint32, little-endian) |

### Формат файла `.data`

Распакованное (после inflate) тело строки.

### Пример вывода для .epf

```
a1b2c3d4-e5f6-7890-abcd-1234567890ab/
│   ├── module.header
│   ├── module.data
│   ├── text.header
│   └── text.data
d5b0e5ed-256d-401c-9c36-f630cafd8a62/
│   ├── form_data.header
│   ├── form_data.data
│   ├── text.header
│   └── text.data
root.header
root.data
version.header
version.data
versions.header
versions.data
```

### Алгоритм `sync_vfs_to_rows`

1. Обратный обход дерева VFS.
2. Для каждой пары `{id}.header` + `{id}.data`:
   - Восстановить `RowHeader` из `.header`.
   - Взять тело из `.data`.
   - Записать в `updates[row_id]`.
3. Для директорий (вложенных контейнеров):
   - Собрать дочерние строки обратно в контейнер с помощью `ContainerWriter`.
   - Записать результат в `updates[row_id]`.

### Особенности

| Свойство | Значение |
|----------|----------|
| Иерархическая структура | ✅ Да — вложенные контейнеры → поддиректории |
| Имена файлов | ID строки + `.header` / `.data` |
| Семантика | Нет — имена остаются техническими |
| Вложенные контейнеры | ✅ Раскрываются рекурсивно |
| Служебные файлы | ✅ Показываются (root, version, versions) |
| Поддержка R/W | ✅ Полная с восстановлением заголовков |
| Совместимость | ✅ v8unpack (классический) — прямая совместимость |

### Отличия от Raw

| Аспект | Raw | V8Unpack |
|--------|-----|----------|
| Заголовки строк | Не сохраняются | Отдельный файл `.header` |
| Вложенные контейнеры | Бинарный блоб | Рекурсивная распаковка |
| Кол-во файлов на строку | 1 | 2 (`.header` + `.data`) |

## 4. Json — читаемая структура для Git

**Файл реализации:** [json.rs](../../src/v8/styles/json.rs)

### Назначение

Семантическое представление содержимого контейнера в виде понятной человеку файловой структуры с именами объектов, модулями `.bsl` и группировкой по типам метаданных. Формат совместим с утилитой [saby-integration/v8unpack](https://github.com/saby-integration/v8unpack) — консольной утилитой для сборки и распаковки бинарных файлов 1С без технологической платформы.

Ключевые принципы формата (в соответствии с saby-integration/v8unpack):

- Структура хранения максимально приближена к структуре метаданных, человекочитаемые имена файлов
- Программный код **всегда** хранится в отдельных `.bsl`-файлах и может быть разделён на несколько файлов
- Служебные метаданные (скобочные структуры `{...}`) конвертируются в JSON для удобства diff
- Двоичные макеты и картинки сохраняются в исходном (бинарном) виде
- Формы декомпозируются: панели и области кода выносятся в отдельные файлы, чтобы минимизировать конфликты при параллельной разработке
- Поддержка индексного файла (`index.json`) для обратной сборки

### Целевая аудитория

- Повседневная работа с файлами 1С в FAR Manager
- Хранение кода в Git с diff-совместимой структурой
- Извлечение модулей для AI-анализа
- Пользователи saby-integration/v8unpack

### Алгоритм `build_vfs`

#### Шаг 1: Определение типа контейнера

1. Если `rows_map` содержит `"configinfo"`, но не содержит `"root"`:
   → **CFE (расширение)** → вызвать `build_extension_vfs`.
2. Иначе разобрать `root`:
   - Прочитать `rows_map["root"]`, извлечь UUID корневого объекта (позиция `[1]` в скобочной структуре).
   - Определить, является ли корневой объект конфигурацией (`is_configuration_format`) или одиночным объектом (EPF/ERF).

Эвристика `is_configuration_format`:

- Проверить наличие в теле корневого объекта UUID-ов групп метаданных (Reports, Catalogs, Documents, DataProcessors). Если найдена хотя бы одна группа → это конфигурация (CF).

#### Шаг 2A: EPF/ERF — одиночный объект (`build_single_object_vfs`)

1. Разобрать заголовок объекта `rows_map[root_uuid]`.
2. Извлечь модуль объекта:
   - Путь в скобочной структуре: `[3][1][1][3][1][1][2]` → UUID модуля.
   - Тело модуля: `rows_map["{uuid}.0"]`.
   - Если тело — вложенный контейнер → извлечь из него строку `"text"`.
   - Создать `VfsEntry::File { name: "ObjectModule.bsl" }`.
3. Перечислить подчинённые объекты (`enumerate_subordinates` из ветки `[3][1]`, начиная с индекса 3):
   - Для каждой группы (Forms, Templates, Commands и т.д.):
     - UUID типа → определить display_name через [uuids.rs](../../src/v8/uuids.rs).
     - Перебрать экземпляры → извлечь имена из заголовков.
4. Построить дерево:
   - **Формы** → `VfsEntry::Dir { name: "ИмяФормы", children: [Module.bsl] }`
   - **Макеты** → `VfsEntry::File { name: "ИмяМакета", data: raw }`
   - **Прочие** → `VfsEntry::File { name: "ИмяЭлемента" }`
5. Сгруппировать в директории по типам: `Forms/`, `Templates/`, `Commands/`.

#### Шаг 2B: CF — конфигурация (`build_configuration_vfs`)

1. Разобрать корневой объект конфигурации `rows_map[root_uuid]`.
2. На верхнем уровне перебрать ветки `[idx]`:
   - Если `[idx][0]` — UUID группы метаданных (`is_metadata_group`) → перечислить типы объектов.
   - Для каждого типа (Справочники, Документы, Отчёты и т.д.):
     - Перебрать экземпляры → извлечь имена (`extract_object_name`).
     - Для каждого объекта → рекурсивно построить поддерево (модули, формы, макеты).
3. Сгруппировать по типам: `Documents/`, `Catalogs/`, `Reports/`, `DataProcessors/`, `CommonModules/` и т.д.

#### Шаг 2C: CFE — расширение (`build_extension_vfs`)

1. Найти UUID корневого дескриптора расширения (самая большая по размеру строка UUID).
2. Разобрать дескриптор аналогично CF.
3. Группировать объекты по типам.

### Пример вывода для .epf

```
ObjectModule.bsl
Forms/
├── ОсновнаяФорма/
│   └── Module.bsl
└── ФормаНастроек/
    └── Module.bsl
Templates/
└── МакетПечати
Commands/
└── КомандаОбработки
index.json
```

### Пример вывода для .cf

```
CommonModules/
├── ОбщийМодуль1/
│   └── Module.bsl
Documents/
├── ЗаказПокупателя/
│   ├── ObjectModule.bsl
│   ├── Forms/
│   │   ├── ФормаДокумента/
│   │   │   └── Module.bsl
│   │   └── ФормаСписка/
│   │       └── Module.bsl
│   └── Templates/
│       └── ПечатнаяФорма
Catalogs/
├── Номенклатура/
│   ├── ObjectModule.bsl
│   └── Forms/
│       └── ФормаЭлемента/
│           └── Module.bsl
Reports/
└── ОтчётПоПродажам/
    └── ObjectModule.bsl
index.json
```

### Алгоритм `sync_vfs_to_rows`

Реализован в функции `sync_nodes_to_map_json`:

1. Рекурсивный обход дерева VFS.
2. Для каждого `VfsEntry::File`:
   - Если `origin_row_id` задан:
     - Если `original_container` задан (модуль был извлечён из вложенного контейнера):
       - Распаковать оригинальный контейнер.
       - Заменить строку `"text"` в нём на новые данные.
       - Пересобрать вложенный контейнер с помощью `ContainerWriter`.
       - Записать результат в `updates[row_id]`.
     - Иначе: записать `data` напрямую в `updates[row_id]`.
3. Для каждого `VfsEntry::Dir`:
   - Рекурсивно обработать дочерние элементы.

### Особенности

| Свойство | Значение |
|----------|----------|
| Иерархическая структура | ✅ Да — семантическая (по типам метаданных) |
| Имена файлов | Человекочитаемые (имена объектов 1С) |
| Семантика | ✅ Полная — Forms, Templates, Commands, типы метаданных |
| Вложенные контейнеры | ✅ Прозрачно раскрываются для извлечения модулей |
| Служебные файлы | ❌ Скрыты (root, version, versions) |
| Метаданные | JSON (конвертация из скобочного формата) |
| Поддержка R/W | ✅ Полная с пересборкой вложенных контейнеров |
| Совместимость | ✅ [saby-integration/v8unpack](https://github.com/saby-integration/v8unpack) |
| Git-пригодность | ✅ Плоская структура, `.bsl` файлы для diff |

## 5. EDT — формат проекта 1C:EDT

### Назначение

Представление содержимого контейнера в формате проектов [1C:Enterprise Development Tools (EDT)](https://edt.1c.ru/) — современной IDE для разработки на платформе 1С:Предприятие на базе Eclipse. EDT хранит конфигурацию как иерархический набор XML-файлов (`.mdo`) и текстовых модулей (`.bsl`), оптимизированный для работы с Git.

Этот стиль повторяет формат, который EDT использует для внутреннего представления проекта. Формат совместим с выгрузкой из Конфигуратора в иерархическом режиме (`/DumpConfigToFiles -Format Hierarchical`), но отличается от неё отсутствием подкаталога `Ext` и более компактными именами метаданных.

### Целевая аудитория

- Разработчики, использующие 1C:EDT
- Интеграция с BSL Language Server и v8-code-style
- Хранение конфигурации в Git в формате, понятном стандартным инструментам 1С
- Миграция между Конфигуратором и EDT

### Формат представления

#### Общие принципы

1. **Метаданные объектов** — файлы `.mdo` (Metadata Object), содержащие XML-описание свойств объекта (имя, синоним, реквизиты, табличные части и т.д.).
2. **Программные модули** — файлы `.bsl` с именами, определяемыми типом модуля (`ObjectModule.bsl`, `ManagerModule.bsl`, `Module.bsl`, `CommandModule.bsl`).
3. **Формы** — описание формы в файле `Form.form` (XML), модуль формы в `Module.bsl`.
4. **Корневой файл** — `Configuration.mdo` (или расширение: `Extension.mdo`) содержит общие свойства конфигурации и перечень всех объектов верхнего уровня.
5. **Нет подкаталога `Ext`** — в отличие от формата Конфигуратора, EDT размещает модули непосредственно в каталоге объекта.

#### Пример структуры для .epf

```

ObjectModule.bsl
Forms/
├── ОсновнаяФорма/
│   ├── Form.form
│   └── Module.bsl
└── ФормаНастроек/
    ├── Form.form
    └── Module.bsl
Templates/
└── МакетПечати/
    └── Template.bin
Commands/
└── КомандаОбработки/
    └── CommandModule.bsl
```

### Алгоритм `build_vfs`

1. Выполнить семантический разбор контейнера (как в Json): определить тип контейнера, разобрать `root`, перечислить объекты метаданных.
2. Для корневого объекта конфигурации:
   - Сформировать `Configuration.mdo` — XML-сериализация свойств конфигурации из скобочной структуры.
3. Для каждого объекта метаданных:
   - Создать каталог с именем объекта.
   - Сформировать `{ИмяОбъекта}.mdo` — XML-описание реквизитов, табличных частей и прочих свойств.
   - Извлечь модули в `.bsl`-файлы:
     - `ObjectModule.bsl` — модуль объекта
     - `ManagerModule.bsl` — модуль менеджера
     - `Module.bsl` — модуль формы, общего модуля
     - `CommandModule.bsl` — модуль команды
   - Для форм: создать каталог `Forms/{ИмяФормы}/` с `Form.form` и `Module.bsl`.
   - Для макетов: создать каталог `Templates/{ИмяМакета}/` с `Template.bin` (или `.mxl`, `.html`).
4. Сгруппировать по типам: `Documents/`, `Catalogs/`, `Reports/`, `DataProcessors/`, `CommonModules/` и т.д.

### Алгоритм `sync_vfs_to_rows`

1. Обратный обход дерева.
2. Десериализовать `.mdo`-файлы обратно в скобочную структуру.
3. Собрать модули в строки контейнера.
4. Пересобрать вложенные контейнеры.

### Особенности

| Свойство | Значение |
|----------|----------|
| Иерархическая структура | ✅ Да — семантическая (по типам метаданных) |
| Имена файлов | Человекочитаемые + `.mdo`, `.bsl`, `.form` |
| Семантика | ✅ Полная — XML метаданные + раздельные модули |
| Метаданные | XML (файлы `.mdo`) |
| Описание форм | XML (файлы `.form`) |
| Подкаталог `Ext` | ❌ Нет — модули лежат в каталоге объекта |
| Совместимость | ✅ 1C:EDT, BSL Language Server |
| Git-пригодность | ✅ Высокая — оптимизирован для diff/merge |
| Поддержка R/W | ✅ С сериализацией/десериализацией XML |

## 6. Configurator — формат выгрузки Конфигуратора

### Назначение

Представление содержимого контейнера в формате, который создаёт встроенный в платформу 1С **Конфигуратор** при выгрузке конфигурации в файлы (меню «Конфигурация → Выгрузить конфигурацию в файлы...» или `/DumpConfigToFiles`). Используется иерархический формат (`-Format Hierarchical`), доступный с платформы 8.3.7.

Этот формат содержит **больше служебных данных** и использует **более длинные пути** по сравнению с EDT, т.к. модули размещаются внутри подкаталога `Ext`.

### Целевая аудитория

- Разработчики, использующие Конфигуратор (а не EDT)
- Совместимость с командой `/LoadConfigFromFiles` для обратной загрузки
- Интеграция с gitsync и другими инструментами, ожидающими формат Конфигуратора

### Формат представления

#### Ключевые отличия от EDT

| Аспект | EDT | Configurator |
|--------|-----|--------------|
| Подкаталог `Ext` | ❌ Нет | ✅ Модули в `Ext/` |
| Метаданные объекта | `{Имя}.mdo` (XML) | `{Имя}.xml` (XML) |
| Описание формы | `Form.form` | `Ext/Form.xml` |
| Модуль объекта | `ObjectModule.bsl` | `Ext/ObjectModule.bsl` |
| Модуль формы | `Module.bsl` | `Ext/Form/Module.bsl` |
| Корневой файл | `Configuration.mdo` | `Configuration.xml` |
| Дополнительные файлы | — | `ConfigDumpInfo.xml` (индекс выгрузки) |

#### Пример структуры для .epf

```

    └── Ext/
        └── Form.xml

└── МакетПечати/
```

```
      │
      ▼

      │
      ▼
  rows_map: HashMap<String, Vec<u8>>
      │
      ├──► RawStyle::build_vfs()            ──► Плоский список файлов (UUID)

      ├──► JsonStyle::build_vfs()            ──► Семантическое дерево (Saby JSON)

                                                    │
                                                    ▼
                                              Vec<VfsEntry>
                                                    │
                                              ┌─────┴─────┐
                                              │           │
                                        Панель FAR   Распаковка на диск
```

## Реализация в коде

### Связь настроек и стилей

Настройка `UnpackStyle` в [settings.rs](../../src/far/settings.rs) определяет числовой код:

| Код | Стиль | Enum |
|-----|-------|------|
| 0 | Raw | `UnpackStyle::Raw` |
| 1 | Full-parse | `UnpackStyle::FullParse` (default) |
| 2 | V8Unpack | `UnpackStyle::V8Unpack` |
| 3 | Json | `UnpackStyle::Json` |
| 4 | EDT | `UnpackStyle::Edt` |
| 5 | Configurator | `UnpackStyle::Configurator` |

Диспетчеризация в [panels.rs](../../src/far/panels.rs):

```rust
pub fn get_style(&self) -> Box<dyn PresentationStyle> {
    match self.settings.unpack_style {
        UnpackStyle::Raw          => Box::new(RawStyle),
        UnpackStyle::FullParse    => Box::new(FullParseStyle),
        UnpackStyle::V8Unpack     => Box::new(V8UnpackStyle),
        UnpackStyle::Json         => Box::new(JsonStyle),
        UnpackStyle::Edt          => Box::new(EdtStyle),
        UnpackStyle::Configurator => Box::new(ConfiguratorStyle),
    }
}
```
